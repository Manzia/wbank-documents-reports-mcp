## Findings for Roy

### F1. Rate-based rules count only above their limit

Check 6 expects `CountedRequests` for rules 2 and 3. A rate-based rule's action, including Count, only
triggers for an IP once its request rate goes over the rule's limit (3,000 or 300 per 5 minutes). Until
then the rule doesn't match, so it emits no `CountedRequests`. AWS's `RateBasedStatement` reference
says: "triggers the rule action when the rate exceeds a limit that you specify". This session sent 8
requests through CloudFront, so 0 is the correct value for both rules. There is no CloudWatch metric for requests
that a rate rule merely evaluated: WAF tracks those rates internally. The session policy denies WAF
reads (`GetRateBasedStatementManagedKeys`, sampled requests), so the session can't see them either.

Rule 2 also can't match from this machine at all, because its scope-down is the AI-platform IP sets.

**Options (Roy to choose):**
- **A (recommended).** Accept check 6 as: no `BlockedRequests` for this traffic, `AllowedRequests`
  counted it, and `CountedRequests` is 0 because the traffic stayed under the limits. Whether the rate
  rules fire is then judged from real traffic during the COUNT week (MCP-170).
- **B.** Exercise rule 3 once: send about 320 `initialize` requests through the endpoint within
  5 minutes from this IP, then confirm `CountedRequests` for `per-ip-rate` and no `BlockedRequests`.
  That costs about 320 Lambda invocations. It is deliberate load on prod, so it needs your approval.
  Rule 2 stays unverifiable from here either way.
