## Findings for Roy and later tasks

### F1. Bedrock refuses Claude 5.5 for this account

`aws bedrock-runtime converse --model-id us.anthropic.claude-haiku-5-5 …` returns
**AccessDeniedException**. The message changed between two calls about an hour apart:
first "Your account is currently being verified…" (also for `global.anthropic.claude-haiku-5-5`
and `us.anthropic.claude-sonnet-5-5`), then "anthropic.claude-haiku-5-5 is not available for this
account". The inference profiles are listed as `ACTIVE`, but every **applied** tokens-per-minute
quota for the Claude 5.5 models is **0** (AWS defaults 6M to 30M). This blocks MCP-131 (Haiku
helpers), MCP-121 and MCP-150 (Sonnet agent, Opus judge).

**Cause (2026-11-23, interactive session with Roy).** Two things, both outside the code:
- **No model agreement.** `aws bedrock get-foundation-model-availability` showed
  `agreementAvailability: NOT_AVAILABLE` for `anthropic.claude-{haiku,sonnet,opus}-5-5`
  (authorization, entitlement and Region all available). Bedrock creates the agreement on the first
  invocation only if the caller may `aws-marketplace:Subscribe`
  ([model access](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html#model-access-permissions));
  the session policy has no Marketplace actions, so the session's first call couldn't start it.
- **Zero quotas.** The applied cross-region TPM quotas were still 0, which an agreement alone
  doesn't change.

**Done (Roy approved):** as `wb-mcp`, `aws bedrock create-foundation-model-agreement` for the three
models (status then `PENDING`), and `aws service-quotas request-service-quota-increase` to the AWS
defaults for L-47520EB7 (Haiku, 10,000,000), L-94A31E46 (Sonnet, 6,000,000) and L-A4430697 (Opus,
30,000,000), status `PENDING`. Once the agreements read `AVAILABLE` and the quotas are applied, re-run
`node scripts/checks/prechecks.mjs --only 4`. The session policy stays as it is: Lambda's execution
role and sessions don't need Marketplace actions once the agreement exists.

### F2. Page breaks are not always form feeds

The design (§2, §5.4) says full-text files keep form-feed page breaks. That holds for the older
P117635 files (ICR 71, PAD 133, ISR 12, procurement plan 7 form feeds). It mostly does not hold for
2026 files:

- Most recent ICRs, PADs, financing agreements and procurement plans use centred `-N-` or
  `Page N` footer lines.
- Short recent ISRs have neither.
- Of 12 recent financing and loan agreements sampled separately, 1 had form feeds.

**For MCP-133:** split on form feeds, else on footer lines, else into fixed-size parts with no
page numbers, and say which one in the coverage note. This changes how `read_document` splits a
file, not what components exist, but it corrects a **[Verified]** line in the design.

### F3. `documents.worldbank.org` is outside the session allow-list

The sandbox network allow-list (`session-settings.json`) has `documents1` but not
`documents.worldbank.org`. The proxy refuses the connection, so check 2's "403 on
`documents.worldbank.org`" couldn't be observed. The script reports such a refusal as
`BLOCKED`, never as a 403. **To finish check 2:** run `node scripts/checks/prechecks.mjs --only 2`
in your own terminal (outside the sandbox). I did not work around the sandbox.

**Run outside the sandbox (2026-11-23, Roy's Mac, interactive session):** `--only 2`, 26 requests,
23 s. `documents1` results match the table below except for newer ISR and financing-agreement samples
(also 0 form feeds). All 5 `documents.worldbank.org` requests answered **301** (`server: cloudflare`)

design's "403" no longer holds from this address; fetching only from `documents1` is unaffected.

### F4. Facets stop at 100 values

Both APIs return at most 100 values per facet. Parameters such as `fct_limit` and `fctlimit` change
nothing, and the API documentation page couldn't be read (F3). The script rebuilds a capped list from
the same facet inside each value of a partition field (WDS: `majdocty_exact`, then `admreg_exact`,
then year ranges; Projects: `regionname_exact`, `status_exact`, then year ranges). It flags a list
as incomplete when a partition still hits the cap, when the partitions don't cover every record, or
when its 200-request budget runs out.

| Filter (design §7.2) | API, facet | Values found | Complete? |
|---|---|---|---|
| countries | WDS `count_exact` | 435 | no: 53 partitions still at the cap when the 200-request budget ran out |
| regions | WDS `admreg_exact` | 10 | yes (1 request) |
| document types | WDS `docty_exact` | 217 | not guaranteed: passes the coverage check (9 requests), but an earlier run found 258 (see note) |
| languages | WDS `lang_exact` | 188 | no: 10,954 "Project Documents" records have no `admreg` (30 requests) |
| countries | Projects `countryshortname_exact` | 209 | no: 2,853 projects have no `regionname` (11 requests) |
| regions | Projects `regionname_exact` | 9 | yes (1 request) |
| sectors | Projects `sector_exact` | 160 | no: undated projects in 7 capped partitions (95 requests) |
| themes | Projects `theme_exact` | 73 | yes (1 request) |
| statuses | Projects `status_exact` | 4 | yes (1 request) |

Note: the runs on `438e94a` found 258 document types and 192 languages, because one
`majdocty_exact` partition value was the empty string, which the API seems to treat as no filter.
Skipping that value gave 217 and 188. The coverage check (`709a30c`) catches records missing from
the language partitions. For document types the partition counts add up, but the 41 extra values
show that the list is still not complete. WDS `count_exact` mixes countries with regions and
groupings ("World", "Africa").

**For MCP-135:** only regions, themes and statuses come back complete in one request. The other
lists can't be shown complete from facets: the cap, records without the partition field, and
undated records all leave gaps, and even an incomplete list costs tens to hundreds of paced requests
(≥ 3 s apart). Choose between accepting a best-effort union (the snapshot says so) and finding
another source for the value lists.

### F5. Sorting and dates

- `srt=docdt&order=desc` is in date order. `order=asc` puts records **without** `docdt` (15 of the
  first 50) and placeholder dates (year 1) first. "Oldest" needs those filtered out (MCP-130).
- Projects `srt=boardapprovaldate&order=desc` sorts. `srt=closingdate&order=asc` does **not**
  (2028-12-31 before 2027-07-16). "Closing soonest" must sort in tool code, as design §5.2 assumed.
- `strdate` without `enddate` returns a different set (38,995 records for `strdate=2023-01-01`,
  149,662 with any `enddate`). **Always send both** (MCP-130).
- `fl` is honoured, but WDS always adds `display_title, pdfurl, guid, url` and Projects always adds
  `project_name, url, project_abstract`.

### F6. Upstream throttling

`search.worldbank.org` returned 503 on 2 back-to-back requests and on several multi-facet requests.
The design's "at most 3 parallel requests per tool call" may draw 503s. The transport's retry with
backoff (design §5) is needed, not optional (MCP-130).

### F7. Gateway rate limits: connections are a rate, not a concurrency cap

`AWS::BedrockAgentCore::GatewayRateLimit` entries take `Requests` (per second or minute), `Tokens`
and `Connections`, and the schema describes `Connections` as "per second only". Design §8.3's
"concurrent connections: 100" can't be expressed as a concurrency cap. MCP-140 should set a
connection rate or leave it out; that is your decision.

### F8. SDK release age

`@hono/aws-lambda@1.0.2` and `hono@4.13.20` were both published on 2026-11-22, one day before this
check. The previous releases are `1.0.1` (2026-10-08) and `4.13.19` (2026-11-16).
`@modelcontextprotocol/server@2.4.0` is 30 days old and matches the design. MCP-112 pins exact
versions; choose whether it pins the newest releases or the previous ones.
