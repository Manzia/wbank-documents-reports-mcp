## Keychain (plan §2.4, "What remains outside the guard")

**Result: FOUND, inferred and not tested directly. Accepted by Roy as a known gap.**
- `! touch ~/.npm/x` succeeded in the self-test session, so `!` commands run **outside** the sandbox.
  The FOUND those `!` commands printed says nothing about sessions.
- The direct test needed the session's own Bash tool to run the script. In the first run auto mode
  refused it, and in the second the model's safety filter refused it.
- The evidence for FOUND comes from the Evoke dispatcher (`wbank-evoke-agent`):
  - Its sessions run `gh` under the same strict sandbox settings with no token of their own, and they
    open PRs.
  - Roy's `gh` stores its token in the Keychain (`gh auth status`: keyring).
  - So sandboxed processes can query the login Keychain.
- **Meaning:** a script a session writes and runs could read Roy's own `gh` token. That token can
  merge PRs and approve `production` deployments, so layers 5 and 6 don't hold against that script.
  What remains is Roy reading each PR before merging and approving.
- This is the same exposure the Evoke and Pivot (`manzia-trust-platform`) dispatchers already run with.
  Roy decided not to move `gh` to file storage.
- To close it later: `gh auth logout -h github.com && gh auth login -h github.com --insecure-storage`.
  That moves the token to `~/.config/gh/hosts.yml`, which the sandbox denies. Then re-run the self-test.
